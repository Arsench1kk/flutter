## Version constraints

I ran `flutter pub add shared_preferences flutter_secure_storage path_provider image_picker permission_handler url_launcher`. Pub wrote `^2.5.6`, `^11.2.0`, `^2.1.6`, `^1.2.4`, `^13.0.2` and `^6.3.3`, respectively. The app's `http: ^1.2.0` accepts versions from `1.2.0` up to, but excluding, `2.0.0`. For example, `1.2.1` and `1.6.0` are allowed. `1.1.2` is below the minimum and `2.0.0` is the next major version. The app commits `pubspec.lock` to give everyone the same exact dependency tree. The resolved version of `http` is `1.6.0`.

An exact `http: 1.2.0` pin failed to resolve in the full app. That version needs `web >=0.3.0 <0.5.0`, while the current permission plugin's web implementation needs `web >=0.5.1 <2.0.0`. I reproduced the requested pin in an isolated fixture with `http` alone. Its lockfile pinned `1.2.0`, and `flutter pub outdated --show-all` showed current/upgradable at `1.2.0` and resolvable/latest at `1.6.0`. The app keeps the caret.

`flutter pub outdated` reported `cupertino_icons` at `1.0.9` with `2.0.0` available. I kept the existing major-version constraint because Practice 12 does not need a Cupertino icon migration.

## Settings and storage

- `main()` initializes Flutter bindings, reads dark mode, the city and the saved session, then calls `runApp()`. A late theme read would start Flutter with the default light theme. `SettingsModel` publishes each change right away and writes preferences in order.
- Ordinary preferences are readable app data. Legacy Android SharedPreferences stores XML in the app sandbox, the default Android backend of `SharedPreferencesAsync` uses Preferences DataStore, and iOS uses a UserDefaults plist. A backup that includes these files, root access or an authorized debugging connection to a debuggable build can expose them. [Preferences storage backends](https://pub.dev/packages/shared_preferences#storage-location-by-platform)
- The fake token goes in secure storage. The iOS Keychain can retain an item's value after uninstall and allow the same app to read it after reinstallation. Treat that behavior as platform-dependent and use sign out to delete the token explicitly.
- On Android, removing or resetting the secure lock screen can permanently invalidate Keystore keys bound to user authentication. A session encrypted with such a key can require a new sign-in. The effect depends on how the key was configured. [Android Keystore documentation](https://developer.android.com/reference/android/security/keystore/KeyPermanentlyInvalidatedException)
- The cache lives at `Documents/users.json`. Each successful GET replaces it. The app can show a saved list while it checks the connection, and shows the offline banner after a connection failure. A missing or unreadable cache falls back to the Offline screen. The avatar is copied to `Documents/avatar.jpg`, and preferences store its Documents-relative path so the photo still resolves if iOS relocates the app container. The OS or a cache-clearing operation can delete files in the temporary directory.

## Camera, photos and links

On modern Android, deny the camera request twice. The plugin can return `permanentlyDenied` on the second denial itself, and subsequent requests reach the app's dialog without a system prompt. **Open settings** opens the app's settings page. On iOS a single denial can be permanent for subsequent requests. A separate Photos authorization state is **Limited**, which permits access to selected photos. **Restricted** means the OS blocks access, for example due to parental controls. [Permission status reference](https://pub.dev/documentation/permission_handler/latest/permission_handler/PermissionStatus.html)

The profile requests camera access on **Take photo**. If the picker returns `null`, the current avatar stays in place. External links use `mailto:`, `tel:` or `https:` and the UI handles a missing handler. A plain website value such as `kbtu.edu.kz` is a relative URI. Adding `https://` gives the launcher an external URL.
